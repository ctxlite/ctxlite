# Feature Specification: OpenCode Output Token Efficiency

**Feature Branch**: `026-opencode-output-token-efficiency`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "eficienta ctx lite este redusa si buggy, as vrea sa ne focusam pe opencode (o sa fac in timp retire la cursor si claude code), dar as vrea sa ne focusam pe eficienta opencode output tokens ca aia sunt scumpi, valorile din grafic apar si nu apar tot timpul, estimarile sunt nerealiste pe cat economiseste deoarece nu vad nici un reduction in cost — as vrea ca toolul sa faca ce zice ca face si sa ne focusam pe reducerea costului pe output unde conteaza fara sa afectam performanta si inteligenta modelului, si sa il blocam sa citeasca fisiere etc. As vrea sa fie build packetul fara sa fie stuck pe o versiune de node, instalarea sa fie seemless, sa faci teste si statistici estimate realiste care sa ne dea un produs care face ce era intuit sa faca: reducerea costului de output token pana la 90% si nu mai slab de 70%."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Trustworthy savings dashboard (Priority: P1)

As a developer running OpenCode with ctxlite installed, I want the savings/stats view to reliably show accurate, real numbers every time I check it, so that I can trust the tool is actually doing what it claims instead of sometimes showing values and sometimes showing nothing.

**Why this priority**: The user's core complaint is that reported numbers are flaky and don't correspond to observed cost reduction. Without a trustworthy measurement, no other improvement in this feature can be verified — this is the foundation everything else is checked against.

**Independent Test**: Run a series of OpenCode coding sessions with ctxlite active, then query the stats/dashboard view after each session. Every query must return consistent, present values (no missing/blank data points), and those values must match the actual measured output-token cost difference for that session.

**Acceptance Scenarios**:

1. **Given** a completed OpenCode session where ctxlite tools were used, **When** the user requests savings stats, **Then** the stats are present and reflect real measured output-token savings for that session (not an estimate disconnected from actual usage).
2. **Given** repeated stats queries across multiple sessions in a row, **When** the user checks the dashboard/graph each time, **Then** values are shown consistently on every query — never intermittently blank or missing for sessions that have completed.
3. **Given** a session where ctxlite had no opportunity to save tokens (e.g., no qualifying reads occurred), **When** the user checks stats, **Then** the dashboard shows zero/no-data for that session rather than a fabricated non-zero number.

---

### User Story 2 - Enforced token-efficient file access in OpenCode (Priority: P1)

As a developer, I want the OpenCode coding agent to be prevented from doing expensive, full-content file reads when a cheaper ctxlite alternative would do the job, so that output token cost is actually reduced instead of relying on the agent optionally following a suggestion.

**Why this priority**: The user explicitly asked to "block" the agent from bypassing ctxlite. Soft instructions already exist (see the project's conciseness rules) and are not producing real savings — enforcement is what turns intent into measured cost reduction, and it is the direct lever on the 70–90% target.

**Independent Test**: In a live local OpenCode session, ask the agent to inspect a large file's structure (not edit it). Confirm the native full-content read is denied/blocked and the agent is redirected to retry with the token-efficient tool, while a task that genuinely requires exact content for an edit still succeeds with a full read.

**Acceptance Scenarios**:

1. **Given** an OpenCode agent attempting a native full-file read on a file above the efficiency threshold purely to understand its structure or API, **When** a token-efficient alternative exists, **Then** the native read is blocked with a message directing the agent to the ctxlite alternative, and the agent must retry through that path.
2. **Given** an OpenCode agent that is about to edit a file and needs exact byte-for-byte content, **When** it performs a full read for that purpose, **Then** the read is allowed and not blocked.
3. **Given** a small/trivial file where a full read is already cheap, **When** the agent reads it, **Then** the system does not force a token-efficient path that would add overhead without benefit.

---

### User Story 3 - Realistic, model-in-the-loop validation (Priority: P2)

As the maintainer, I want tests and statistics that are generated by actually invoking OpenCode locally against real (free-tier) models with logging and rerun support, so that the 70–90% output-token-cost-reduction claim is backed by evidence from real sessions instead of synthetic assumptions.

**Why this priority**: The user's stated distrust ("nu vad niciun reduction in cost") comes from estimates that don't hold up against reality. This story makes the measurement methodology itself trustworthy, which is what makes Success Criteria SC-001–SC-003 below verifiable rather than aspirational.

**Independent Test**: Run the test/benchmark harness end-to-end locally: it invokes OpenCode against a real, freely-available model, once with ctxlite's enforcement active and once with it disabled, on the same representative task set; it logs per-run token/cost data, and can be rerun to confirm the measured reduction is stable across runs.

**Acceptance Scenarios**:

1. **Given** a defined set of representative coding tasks, **When** the benchmark harness runs them through a real local OpenCode invocation with ctxlite active, **Then** it records actual output token counts and derived cost per task, per model.
2. **Given** the same task set, **When** the harness reruns it with ctxlite's enforcement disabled, **Then** it records the same metrics for comparison as the baseline.
3. **Given** two or more reruns of the same task set under the same conditions, **When** results are compared, **Then** the measured output-token reduction is stable (not wildly divergent between runs) and logged for inspection.
4. **Given** a benchmark run that also scores task correctness/output quality, **When** ctxlite enforcement is active vs. disabled, **Then** correctness/quality does not measurably regress.

---

### User Story 4 - Seamless install/build not pinned to a Node version (Priority: P3)

As a developer installing ctxlite for OpenCode, I want the package to build and install cleanly regardless of which supported Node.js version I have, so that setup doesn't fail or require me to switch Node versions first.

**Why this priority**: This is an adoption blocker rather than a correctness issue — it doesn't affect token savings once installed, but a failed/painful install prevents the rest of the feature from being used at all.

**Independent Test**: Perform a fresh install of the OpenCode-targeted package on each supported Node.js version (current and previous LTS at minimum) in a clean environment and confirm it completes without manual intervention or version-specific failures.

**Acceptance Scenarios**:

1. **Given** a clean environment on the oldest supported Node LTS version, **When** the user installs the package, **Then** installation completes successfully with no manual steps beyond the standard install command.
2. **Given** a clean environment on the newest supported Node LTS version, **When** the user installs the package, **Then** installation completes successfully with the same command and outcome.
3. **Given** an install failure caused by a native dependency mismatch, **When** it occurs, **Then** the error clearly identifies the cause instead of a generic failure.

---

### Edge Cases

- What happens when a native file read is blocked but the agent has no ctxlite-equivalent tool available in its current toolset (e.g., misconfigured OpenCode setup)? The system must not leave the agent stuck with no way to read the file — it should fail toward an accurate, non-fabricated stats state rather than silently degrading.
- What happens when output-token cost data isn't available for the model/provider in use (e.g., pricing unknown)? The dashboard must show the data as unavailable rather than inventing a number.
- How does the system handle a file that is borderline-sized (near the efficiency threshold) — does blocking behavior flip-flop between sessions? Threshold behavior must be deterministic for a given file.
- What happens if a benchmark rerun against a free-tier model hits a rate limit or the model is temporarily unavailable? The harness must record the run as inconclusive/failed rather than silently reporting misleading numbers for that run.
- What happens on Cursor/Claude Code integrations (not the focus of this feature) while OpenCode-specific enforcement ships? They must continue functioning as they do today — this feature does not remove or degrade them, per the user's stated plan to retire them separately over time.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST prioritize OpenCode as the primary integration target for output-token efficiency work in this feature, while leaving existing Cursor and Claude Code integrations functioning without regression.
- **FR-002**: The system MUST record and report actual measured output-token savings per OpenCode session, derived from real tool-call data, not from a theoretical/static estimate.
- **FR-003**: The stats/dashboard view MUST return consistent results on every query for a completed session — it MUST NOT intermittently omit or fail to display data that exists.
- **FR-004**: When no qualifying savings occurred in a session, the system MUST report zero/no-data rather than a non-zero fabricated value.
- **FR-005**: In OpenCode sessions, the system MUST block a native, full-content file read when a token-efficient ctxlite alternative (e.g., structure-only read) would satisfy the agent's evident purpose, and MUST direct the agent to retry via the token-efficient alternative.
- **FR-006**: The system MUST allow full-content native reads to proceed without blocking when the agent's evident purpose requires exact content (e.g., immediately prior to an edit of that file).
- **FR-007**: The system MUST NOT apply blocking/enforcement overhead to files small enough that a full read is already cheap (below the efficiency threshold).
- **FR-008**: The system MUST provide an automated benchmark/test harness that invokes OpenCode locally against real, freely-available models to measure output-token cost with ctxlite enforcement active versus disabled, on the same representative task set.
- **FR-009**: The benchmark harness MUST log per-run token counts, derived cost, and task identifiers, and MUST support being rerun to check stability of the measured reduction across runs.
- **FR-010**: The benchmark harness MUST also measure task correctness/output quality alongside token cost, so that cost reduction is not credited if it comes from degraded model behavior.
- **FR-011**: The system MUST achieve a measured output-token cost reduction, per the benchmark harness, of at least 70% and up to approximately 90% for representative OpenCode coding tasks, compared to the same tasks run with ctxlite enforcement disabled.
- **FR-012**: The system MUST NOT cause a measurable regression in task correctness/completion quality as a result of the enforcement introduced by this feature.
- **FR-013**: The package build/install process targeting OpenCode MUST succeed on all currently-supported Node.js LTS versions without requiring the user to pin to a specific version.
- **FR-014**: Install failures caused by environment/native-dependency mismatches MUST surface a clear, specific error rather than a generic failure.

### Key Entities

- **OpenCode Session**: A single coding session run through OpenCode with ctxlite active; has a set of tool calls, measured output tokens, and derived cost.
- **Efficiency Enforcement Rule**: The policy that determines, for a given file and agent intent (structural inspection vs. edit), whether a native read is blocked and redirected to a ctxlite-equivalent tool.
- **Savings Record / Stat**: A persisted measurement tied to a session, holding real observed output-token savings (not an estimate), used to populate the dashboard/graph.
- **Benchmark Run**: One execution of the representative task set against a real local OpenCode invocation and a specific free-tier model, in either "ctxlite enforced" or "ctxlite disabled" mode, producing logged token/cost/quality data.
- **Task Set**: The representative collection of coding tasks used consistently across benchmark runs so reductions are comparable run-to-run.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Across the representative OpenCode task set, output-token cost is reduced by at least 70% (target up to ~90%) compared to the same tasks run with ctxlite enforcement disabled, as measured by real local OpenCode benchmark runs.
- **SC-002**: The measured reduction in SC-001 is stable across repeated benchmark reruns under the same conditions (no wild run-to-run divergence that would indicate the number is not real).
- **SC-003**: Task correctness/output quality on the benchmark set shows no measurable regression between ctxlite-enforced and ctxlite-disabled runs.
- **SC-004**: When a user queries savings stats after any completed OpenCode session, correct data is present 100% of the time (no intermittently missing dashboard values) across at least 20 consecutive sessions in validation testing.
- **SC-005**: Reported savings numbers match independently recomputed real token/cost differences for the same session within a small tolerance, with zero instances of a fabricated non-zero value on a no-savings session.
- **SC-006**: At least 95% of native full-content file reads in OpenCode sessions that had a qualifying token-efficient alternative and no evident edit intent are blocked and redirected, measured across benchmark and validation sessions.
- **SC-007**: A fresh install of the OpenCode-targeted package succeeds without manual version-pinning steps on both the current and previous Node.js LTS versions.

## Assumptions

- "Output tokens" refers to the tokens the model generates in its responses/tool calls during a session, since these are the cost driver the user called out as expensive; input/prompt tokens are out of scope for the 70–90% target unless they are a direct side effect of the same enforcement.
- The representative task set for benchmarking will be drawn from realistic OpenCode coding workflows already exercised by ctxlite's existing efficiency tools (smart_read, trim_context, code_search, etc.); it does not need to cover every code path in the repository, only be broad enough to reflect typical usage.
- "Free-tier / freely-available models" for local benchmark validation means whatever no-cost model access is available to the maintainer through OpenCode at the time tests run (the specific model/provider is a benchmark-harness implementation detail, not a spec-level constraint, since free-tier availability changes over time).
- "Evident edit intent" (used to decide whether a full read is allowed) is inferred from the agent's own signaled purpose/tool sequence in the same way the project's existing conciseness guidance already distinguishes "read to edit" from "read to understand" — this feature makes that distinction enforced rather than advisory.
- Cursor and Claude Code integrations are explicitly out of scope for new efficiency work in this feature; the only requirement on them is "no regression," per the user's stated intent to retire them separately later.
- "Currently-supported Node.js LTS versions" means the active and maintenance LTS lines at the time this feature ships, consistent with standard Node.js release practice, not a specific hardcoded version pin in the package.
